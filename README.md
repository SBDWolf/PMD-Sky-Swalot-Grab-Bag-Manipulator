# PMD Sky Swalot Grab Bag Manipulator

The bulk of this web app has been AI-generated (by a local model). It has been tested to work as expected and manually adjusted a little in its presentation. Below is the original Readme as generated by the model. To understand how manips work, refer to the [article on the PMD Speedrunning Wiki](https://pmdspeedruns.miraheze.org/wiki/EoS_Bazaar_Manipulations).

-----

A small static web tool (no build step, no backend) that computes the **fastest
Secret Bazaar (Swalot grab bag) RNG manipulations** from externally stored item
tables. Pick a dungeon, pick the items you want, and it outputs the fastest
sequence of dashing/attacking/partner talks that lands you on each item.

## How to use it

1. Open `index.html` (via GitHub Pages, or locally with a web server — see below).
2. Pick a **mode**:
   * **Story Dungeons** (default) — only the story dungeons, only the story
     item list, and the team size is locked per dungeon (greyed out).
   * **Free Selection** — all dungeons, all items, any team size.
3. Set a quantity next to each item you want (0 = skip).
4. The **Fastest manipulation** panel updates automatically:

   ```
   Partner talks | 4-tile dashes | Attacks | Item received
   --------------|---------------|---------|-------------
   0             | 11            | 1       | Joy Seed
   0             | 2             | 0       | Joy Seed
   1             | 11            | 3       | Joy Seed
   Total time: 140  (100 passed turns, 1 partner talk × 40)
   ```

   Each row is one item to collect: the raw number of partner talks, 4-tile
   dashes (4 turns each) and failed attacks (1 turn each) to perform before
   talking to Swalot — 0 means that action isn't used. The order of the
   actions within a row doesn't matter; only the counts matter.
5. **Copy summary** puts a compact one-liner (e.g.
   `Sky Peak (team 4): 1.T45 [89@406] 2.T8 [89@481] 3.T47P1 [89@910] | total 140`)
   on your clipboard.

### Local run

The page loads its data with `fetch()`, so double-clicking `index.html` won't
work in Chrome. Either:

```
python -m http.server
# then open http://localhost:8000/
```

or deploy to GitHub Pages (see below).

### GitHub Pages deployment

1. Push the repo to GitHub.
2. In **Settings → Pages → Build and deployment → Source**, select **GitHub Actions**.
3. Push to `main` — the workflow in `.github/workflows/deploy-pages.yml` deploys
   the whole repo root.

## The model

* Position `p` (1-indexed) is the `p`-th draw in a dungeon's table: the item
  Swalot sells when you talk to him there. **Position 1** is the draw you get
  by talking to Swalot immediately after a full reset.
* Advancing the PRNG:
  * pass one turn (dash one tile, or one failed attack): **+6 / +7 / +8 / +9**
    positions for team sizes 1–4, time cost **1**;
  * talk to a partner: **+3** positions, time cost **40** (≈10 dash cycles);
  * talk to Swalot (collect): **+3** positions, time cost **0**.
* You may collect several wanted items in one run (the PRNG keeps advancing),
  and the solver **never** talks to Swalot for an item you didn't ask for.
* The time costs are fixed in `js/solver.js` as `DEFAULT_COSTS` (partner 40,
  turn 1, collect 0) — edit that constant if your model differs.

Because every action strictly advances the position, the solver is a single
forward dynamic program over `(position, remaining-quantity-vector)` — exact,
not heuristic. It keeps a 10M-state safety cap so solving stays under a second
in the browser; bigger combinations just get a friendly "too large" error.

## Data files

The web app never reads the original `Data/*.txt` files — it reads converted
JSON:

| File | Purpose |
| --- | --- |
| `Data/tables/<id>.json` | one dungeon table: `{id, version, length, items[], rng[]}` |
| `Data/registry.json` | maps dungeon display names → table ids (one table can back several dungeons, e.g. Crystal Cave → Crystal Crossing / Treeshroud Forest, Amp Plains → Far Amp Plains) |
| `Data/item-names.txt` | the source item list: one `0x<hex id>  <English name>  <Japanese name>` per line (ids `0x0`–`0x577`). |
| `Data/items.json` | item id → `{name, icon}`. Icons may be an emoji/text or an image path — put images in `Data/icons/` (e.g. `"icon": "Data/icons/26.png"`). **Names are regenerated from `Data/item-names.txt` by `tools/import_items.py`** (hex id → decimal key, English name used verbatim — `$$$` rows are kept, those items are never drawn). Re-running the importer preserves any `icon` values and entries for ids not in the list. |
| `Data/relevant.json` | the **mode** definition. The `story` mode lists its item ids and an explicit dungeon → team-size map; only dungeons listed there are selectable in Story Dungeons (so dungeons you import later won't appear there until you add them), and the listed team size is enforced (the team dropdown is greyed out). **The item list is still a placeholder (Power Band, Warp Scarf, Revive, Joy Seed, Foe Hold, Link Box) — edit to taste.** |

### Adding a new dungeon table

```
python tools/import_table.py "Data\grab bag manip bot new dungeon.txt" --dungeon "New Dungeon"
```

The tool validates the file (iterations must be exactly `1..N`; a file with two
tables concatenated — iterations restarting at 1 — is rejected with a loud
error), writes `Data/tables/new-dungeon.json`, and registers the dungeon name.
One table can serve multiple dungeon aliases:

```
python tools/import_table.py "Data\grab bag manip bot crystal cave.txt" \
    --dungeon "Crystal Cave" --dungeon "Crystal Crossing" --dungeon "Treeshroud Forest"
```

`--id <slug>` overrides the table id, `--replace` overwrites an existing table
or re-points an existing dungeon name, and `--list` shows the current state.
Re-importing an unchanged file is a no-op.

### Updating item names

```
python tools/import_items.py [Data\item-names.txt] [--out Data\items.json] [--dry-run]
```

Reads `Data/item-names.txt` (one `0x<hex id>  <English name>  <Japanese name>`
per line), converts the hex ids to the decimal ids the tables use, and merges
the English names into `Data/items.json`. Rows named `$$$` are kept as-is
(those item ids are never drawn). Existing `icon` values and entries for ids
missing from the list survive re-runs.

### Verifying manips

`tools/reference_solve.py` is a Python reference implementation of the same DP
(useful for double-checking results without the browser):

```
python tools/reference_solve.py Data/tables/sky-peak.json --team 4 --items 89:3
```

## Tests

`test/solver-test.html` is a self-test page (open it the same way as the main
page, e.g. `/test/solver-test.html`). It re-runs 13 fixed cases against the JS
solver and compares them with results generated by `tools/reference_solve.py`
(costs: partner 40, turn 1, collect 0 — the fixed `DEFAULT_COSTS` in
`js/solver.js`). If you change the solver or the cost model, regenerate the
expected values with the reference tool and update `test/solver-test.js`.

## Layout

```
index.html                  the tool
css/style.css               styles
js/solver.js                the DP solver (no dependencies)
js/main.js                  UI controller
Data/tables/*.json         imported dungeon tables (next to the original .txt files)
Data/registry.json         dungeon names → tables
Data/items.json            item names/icons (regenerated from item-names.txt)
Data/item-names.txt        source item list (0x id, English name, Japanese name)
Data/icons/                item icon images (add your own PNGs, e.g. 26.png)
Data/relevant.json         mode item lists + per-dungeon locked team sizes (fill in)
tools/import_table.py       .txt → JSON importer + registry updater
tools/import_items.py       item-names.txt → items.json importer
tools/reference_solve.py    Python reference solver
test/solver-test.html       in-browser solver self-test
Data/                       original .txt tables (kept untouched)
Examples/                   original example script (kept for reference)
```
