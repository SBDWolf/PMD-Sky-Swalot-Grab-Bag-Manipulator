# PMD Sky Swalot Grab Bag Manipulator

The bulk of this web app has been AI-generated (by a local model). It has been tested to work as expected and manually adjusted a little in its presentation. Below is the original Readme as generated by the model. To understand how manips work, refer to the [article on the PMD Speedrunning Wiki](https://pmdspeedruns.miraheze.org/wiki/EoS_Bazaar_Manipulations).

-----

A small static web tool (no build step, no backend) that computes the **fastest
Secret Bazaar (Swalot grab bag) RNG manipulations** from externally stored item
tables. Pick a dungeon, pick the items you want, and it outputs the fastest
sequence of dashing/attacking/partner talks that lands you on each item.

## How to use it

1. Open `index.html` (via GitHub Pages, or locally with a web server — see below).
2. Pick a **mode**:
   * **Story Dungeons** (default) — only the story dungeons, only the story
     item list, and the team size is locked per dungeon (greyed out).
   * **Free Selection** — all dungeons, all items, any team size.
3. Set a quantity next to each item you want (0 = skip).
4. The **Fastest manipulation** panel updates automatically:

   ```
   Partner talks | 4-tile dashes | Attacks | Item received
   --------------|---------------|---------|-------------
   0             | 11            | 1       | Joy Seed
   0             | 2             | 0       | Joy Seed
   1             | 11            | 3       | Joy Seed
   Total time: 140  (100 passed turns, 1 partner talk × 40)
   ```

   Each row is one item to collect: the raw number of partner talks, 4-tile
   dashes (4 turns each) and failed attacks (1 turn each) to perform before
   talking to Swalot — 0 means that action isn't used. The order of the
   actions within a row doesn't matter; only the counts matter.
5. **Copy summary** puts a compact one-liner (e.g.
   `Sky Peak (team 4): 1.T45 [89@406] 2.T8 [89@481] 3.T47P1 [89@910] | total 140`)
   on your clipboard.

### Local run

The page loads its data with `fetch()`, so double-clicking `index.html` won't
work in Chrome. Either:

```
python -m http.server
# then open http://localhost:8000/
```

or deploy to GitHub Pages (see below).

### GitHub Pages deployment

1. Push the repo to GitHub.
2. In **Settings → Pages → Build and deployment → Source**, select **GitHub Actions**.
3. Push to `main` — the workflow in `.github/workflows/deploy-pages.yml` deploys
   the whole repo root.

## The model

The item sequence is **simulated on the fly** — there are no per-dungeon
precomputed tables anymore. `js/rng.js` reproduces the game's grab bag draw
exactly (validated against all the old precomputed tables in
`Data/tables/`, 8000/8000 positions — open `/test/rng-test.html` to re-run):

* The dungeon PRNG is an LCG: `x = (1566083941 * x + 1) mod 2^32`. 16-bit
  draws take the **upper** 16 bits, scaled as `DungeonRandInt(high) =
  (upper16 * high) >> 16`.
* Position `p` (1-indexed) starts from PRNG state `LCG^(p-1)(seed)`, where
  the seed (`a61564cd`) is the dungeon PRNG working value right after a
  quicksave. **Position 1** is the item Swalot sells if you talk to him
  immediately after loading the quicksave.
* Each purchase consumes three rolls:
  1. `DungeonRandInt(100) < 50` → the common pull, always an **Oran Berry**;
  2. `DungeonRandInt(10000)` picks the **category**: first cumulative
     category weight ≥ the roll;
  3. `DungeonRandInt(10000)` picks the **item** inside that category's pool:
     first cumulative item weight ≥ the roll.
* The category weight list and the item pools in the floor XML
  (`ItemList type="Unk1"`) are stored in **different orders** — the pools are
  paired with their categories via item-id ranges, not by position.
* Advancing positions (all strictly advance, so the DP stays exact):
  * pass one turn (dash one tile, or one failed attack): **+6 / +7 / +8 / +9**
    positions for team sizes 1–4, time cost **1**;
  * talk to a partner: **+3** positions, time cost **40** (≈10 dash cycles);
  * talk to Swalot (collect): **+3** positions, time cost **0**.
* You may collect several wanted items in one run (the PRNG keeps advancing),
  and the solver **never** talks to Swalot for an item you didn't ask for.
* The time costs are fixed in `js/solver.js` as `DEFAULT_COSTS` (partner 40,
  turn 1, collect 0) — edit that constant if your model differs.

Because every action strictly advances the position, the solver is a single
forward dynamic program over `(position, remaining-quantity-vector)` — exact,
not heuristic. It keeps a 10M-state safety cap so solving stays under a second
in the browser; bigger combinations just get a friendly "too large" error. If
no path exists within the simulated window the window is automatically
extended (1500 → 6000 draws) before giving up.

## Dungeons

* **Story Dungeons** mode keeps its fixed list (`Data/relevant.json`), with
  per-dungeon locked team sizes. "Sky Peak" resolves to the
  `Sky Peak Summit Pass` floor data.
* **Free Selection** lists every dungeon that can actually spawn a Secret
  Bazaar: a floor with `hidden_stairs != 0` **and** `unk_hidden_stairs` of
  `0` or `255` (verified: those are the only two values in the game's data).
  That's 36 of the 192 dungeons in `dungeon_export/`.

The dungeon list lives in `Data/dungeons.json`, generated from the XML dump:

```
python tools/export_dungeons.py
```

The grab bag item pools themselves are read live from
`dungeon_export/<folder>/floor_001.xml` when you pick a dungeon, so the XML
dump stays the single source of truth. Re-run the exporter after adding or
changing floor data.

## Data files

| File | Purpose |
| --- | --- |
| `Data/dungeons.json` | `{seed, dungeons[]}` — every dungeon with its export folder and a `bazaar` flag (generated by `tools/export_dungeons.py`). |
| `dungeon_export/<folder>/floor_001.xml` | the grab bag item list (`ItemList type="Unk1"`) read at runtime. |
| `Data/tables/*.json` | the old precomputed tables — no longer used by the app, kept as regression data for `/test/rng-test.html` and `tools/reference_solve.py`. |
| `Data/registry.json` | legacy dungeon-name → table map (kept for the reference tools). |
| `Data/item-names.txt` | the source item list: one `0x<hex id>  <English name>  <Japanese name>` per line (ids `0x0`–`0x577`). |
| `Data/items.json` | item id → `{name, icon}`. Icons may be an emoji/text or an image path — put images in `Data/icons/` (e.g. `"icon": "Data/icons/26.png"`). **Names are regenerated from `Data/item-names.txt` by `tools/import_items.py`** (hex id → decimal key, English name used verbatim — `$$$` rows are kept, those items are never drawn). Re-running the importer preserves any `icon` values and entries for ids not in the list. |
| `Data/relevant.json` | the **mode** definition. The `story` mode lists its item ids and an explicit dungeon → team-size map; only dungeons listed there are selectable in Story Dungeons, and the listed team size is enforced (the team dropdown is greyed out). |

### Regenerating the dungeon list

```
python tools/export_dungeons.py
```

Scans `dungeon_export/index.csv` and every `floor_*.xml`, flags dungeons with
at least one Secret-Bazaar-capable floor, and writes `Data/dungeons.json`.

### Verifying the simulation

`test/rng-test.html` simulates each of the six reference dungeons on the fly
and compares every position (item **and** PRNG state) against the
precomputed `Data/tables/*.json` — all must match. Open it the same way as
the main page (e.g. `/test/rng-test.html`).

`tools/reference_solve.py` is a Python reference implementation of the DP
solver (useful for double-checking results without the browser):

```
python tools/reference_solve.py Data/tables/sky-peak.json --team 4 --items 89:3
```

## Tests

* `test/solver-test.html` re-runs 13 fixed cases against the DP solver and
  compares them with results generated by `tools/reference_solve.py` (costs:
  partner 40, turn 1, collect 0 — the fixed `DEFAULT_COSTS` in
  `js/solver.js`). If you change the solver or the cost model, regenerate the
  expected values with the reference tool and update `test/solver-test.js`.
* `test/rng-test.html` validates the on-the-fly PRNG simulation: it must
  reproduce all six precomputed tables exactly (items **and** PRNG states).
